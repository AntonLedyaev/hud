# DIY Head-Up Display — контекст проекта

> Живой документ. Обновляется при принятии решений и переходах между этапами.
> Последнее обновление: 2026-11-06 (выбор архитектуры Этапа 1; реализация ещё не начата)

## 1. Суть проекта

Самодельный HUD-проектор для старых автомобилей: проецирует на лобовое стекло текущую скорость и распознанные камерой дорожные знаки (аналог встроенных систем Traffic Sign Recognition в новых машинах). Пет-проект, разработка ведётся поэтапно — от мобильного MVP до железа в машине.

## 2. Ключевые принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Регион знаков | Германия / ЕС, позже потенциально РФ | Пользователь в Германии; датасеты GTSRB/GTSDB — немецкие знаки |
| Охват знаков в MVP | Ограничения скорости + критичные: STOP, запрет/конец запрета обгона, конец зоны ограничения | Разумный баланс: не только скорость, но без взрыва классов |
| Структура кода | Монорепо (app + ml + hw) | Один пет-проект, общие модели и конфиги |
| Архитектура Android Этапа 1 | Один Gradle-модуль приложения, простые слои по пакетам: UI, session, camera, inference, domain, data | Выбрано 2026-11-06: минимум инфраструктуры, независимая от Android логика состояния для тестов и replay |
| Первый ML-эксперимент Этапа 1 | Одностадийный YOLO с классами из `shared/labels.yaml` | Выбрано 2026-11-06: один детектор вместо связки детектор + классификатор; размер, разрешение и точность экспорта выбираются по качеству и замерам на телефоне |

## 3. Профиль разработчика

- Fullstack-разработчик, основной язык — JavaScript/TypeScript.
- Университетский опыт Python/ML: Keras, TensorFlow, Pandas. PyTorch будет новым, но концепции знакомы.
- Небольшой опыт Android на Java (много лет назад). Kotlin + Compose — новое, но порог входа приемлемый.
- Embedded/Raspberry Pi — новая область.
- Рабочая машина: **Windows**, RTX 3060 (драйвер CUDA 13.x). Влияет на установку torch (см. ml/README.md).
- Вывод для AI-workflow: код можно писать плотно, но по Kotlin/Compose и embedded-части нужны пояснения решений, а не только код.

## 4. Этапы

### Этап 0 — Инфраструктура (текущий)
Цель: готовая среда для работы по этапам.
- Монорепо: структура, .gitignore, README, лицензия.
- AI-workflow: CLAUDE.md / контекст-файлы, конвенции коммитов, harness для проверки (линтеры, тесты, CI позже).
- Python-окружение для ML (uv или conda), Android Studio, базовый скелет обоих подпроектов.
- Definition of Done: `git clone` → окружения поднимаются по README, пустое приложение собирается, ML-скрипт «hello world» тренирует что-то тривиальное на GPU.

### Этап 1 — Мобильный MVP + модель
Цель: телефон на держателе распознаёт знаки в реальной поездке и показывает «текущее состояние» (действующий лимит и активные ограничения).
- Тренировка детектора (YOLO) на GTSDB/Mapillary + классификация классов MVP.
- Экспорт в TFLite, инференс на телефоне (CameraX → анализ кадров → overlay).
- Логика состояния: знак увидели → лимит действует → сброс (конец зоны / новый знак / перекрёсток-эвристика позже).
- Логи поездок в Room (что распознано, когда, с каким confidence) — это же станет источником данных для дообучения.
- Definition of Done: в реальной поездке по городу/автобану приложение стабильно держит актуальный лимит, FPS достаточен, ложные срабатывания терпимы и логируются.

### Этап 2 — Железо
Цель: тот же функционал на Raspberry Pi 5 + камера + ИИ-ускоритель, вывод на OLED/LCD, скорость по GPS-модулю.
- Портирование пайплайна, квантизация/компиляция модели под ускоритель, дообучение при необходимости.
- Закупка железа — в начале этапа, финальный список утверждается тогда (см. риски).

### Этап 3 — Форм-фактор и проекция
Цель: вывод на лобовое стекло (combiner-стекло или проекция на плёнку), корпус, питание от бортовой сети, читаемость днём.

### Этап 4 — Интеграция с машиной
Цель: скорость и данные из CAN через OBD-II адаптер вместо/вместе с GPS.

## 5. Стек

**Android MVP:** Kotlin, Jetpack Compose, CameraX, TensorFlow Lite (LiteRT), Coroutines/Flow, Room. OpenCV — только если понадобится preprocessing.

**ML:** Python, PyTorch, Ultralytics/YOLO, OpenCV, Albumentations. Экспорт: TFLite/ONNX. Тренировка локально на GPU.

**Hardware (Этап 2, предварительно):** Raspberry Pi 5, камера (CSI или USB), ИИ-ускоритель (Coral USB *или* альтернатива — см. риски), OLED/LCD, GPS-модуль, OBD-II адаптер (Этап 4).

## 6. Данные и модель

- **GTSRB** — 43 класса немецких знаков, классификация (~50k изображений). База для классификатора.
- **GTSDB** — детекция знаков на дорожных сценах (900 полных кадров). Маловат сам по себе.
- **Mapillary Traffic Sign Dataset** — 100k+ изображений, глобальное покрытие (пригодится для будущей адаптации под РФ), детекция + классификация.
- **Собственные данные** — логи и кадры из приложения Этапа 1 (дашкам-стайл записи поездок) для дообучения на реальных условиях (ночь, дождь, засветка).
- Выбранный первый эксперимент: одностадийный YOLO с классами из `shared/labels.yaml`; конкретный вариант модели, разрешение и точность экспорта — по результатам экспериментов Этапа 1. Детектор «знак вообще» + классификатор остаётся альтернативой для отдельного решения, если baseline не даст нужного качества.
- Классы MVP: лимиты 30/50/60/70/80/100/120 (+ зона 30), конец лимита / конец всех ограничений, STOP, запрет обгона, конец запрета обгона.

## 7. Риски и известные грабли

- **Google Coral USB — главный кандидат на замену.** Софт-стек (pycoral/edgetpu) практически заброшен Google, официальная поддержка застряла на старых версиях Python, на Pi 5 заводится с костылями. Сильная альтернатива: **Raspberry Pi AI Kit / AI HAT+ (Hailo-8L, 13 TOPS)** — официальный аксессуар для Pi 5 с живой поддержкой. Решение принять перед закупкой к Этапу 2.
- **Электронные/переменные табло** на автобанах (LED-знаки) выглядят иначе, чем печатные знаки в датасетах — вероятный слабый участок модели.
- **Условия съёмки:** ночь, дождь, контровый свет, грязное стекло. Митигируется своими данными и аугментациями.
- **Неявные лимиты:** в Германии лимит часто определяется не знаком, а типом дороги (город 50, вне города 100, автобан — рекомендация 130). Камера этого не видит. Возможный fallback позже — OSM/оффлайн-карты со speed limits.
- **Правовое:** проекция на стекло и крепление устройств регулируются (StVZO в DE). Отметить на Этапе 3; на Этапе 1 телефон в обычном держателе — ок.
- **Безопасность:** проект — ассистент, не источник истины. Не отвлекать водителя, никаких навязчивых уведомлений.
